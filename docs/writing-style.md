# thmm.kr 글쓰기 규칙

케이스 스터디와 블로그를 쓸 때 따르는 기준. **AI가 대신 쓸 때도 이 파일을 먼저 읽는다.**

이 문서는 확정본이 아니라 v1이다. 신성무가 직접 고친 글이 나올 때마다
그 diff에서 규칙을 뽑아 여기에 반영한다.

---

## 0. 어디에 무엇을 쓰나

**글에서 내가 주인공이면 케이스 스터디, 문제가 주인공이면 블로그.**

| | 케이스 스터디 (`/portfolio`) | 블로그 (`/blog`) |
|---|---|---|
| 단위 | 일 한 건 (조직·시스템·기간이 있음) | 조각 하나 (맥락 없이도 읽힘) |
| 독자가 원하는 것 | "이 사람 뭐 하는 사람이지" | "내 에러 어떻게 고치지" |
| 구조 | 문제→접근→구현→결과 완결 | 자유 |
| 언어 | 한국어 + 영어 | 한국어만 |
| 검색어 | `SSO Provider 구축`, 사람 이름 | `iBATIS ROWNUM 대체`, 에러 메시지 |
| 빈도 | 분기에 1~2건 | 자주 |

예) "상용 그리드를 걷어냈다" → 케이스 스터디.
"`ssh -i`는 그 키만 쓰는 게 아니다" → 블로그.

## 0-1. 쓸 가치가 있나 — 발행 기준

"이 정도 얘기를 올려도 되나" 싶을 때 쓰는 기준. **단 하나로 판단한다.**

> **이걸 검색해서 들어올 사람이 있나?**

있으면 쓴다. 소재가 얼마나 대단한지는 상관없다.
`앱인토스 검수 반려 displayName`은 지금 한국어 검색 결과가 거의 없다.
그 순간 막혀 있는 사람에게는 아키텍처 에세이보다 이 글이 백 배 쓸모 있다.

**작은 소재가 하찮아지는 건 소재 때문이 아니라 이렇게 쓸 때다:**

- 사실만 나열하고 끝낸다 (`displayName이 달라서 반려됐다.` 끝)
- 왜 놓쳤는지가 없다
- 그래서 뭘 바꿨는지가 없다

같은 소재라도 **놓친 이유 + 바꾼 것**이 들어가면 남이 쓸 수 있는 글이 된다.
위 세 줄이 다 빠져 있으면 그건 일기다. 안 쓴다.

**안 쓰는 것**

- 검색어가 안 잡히는 신변잡기 ("오늘 뭐 했다")
- 공식 문서를 그대로 옮긴 것 (링크 하나면 된다)
- 겪지 않고 읽기만 한 것

## 1. 어미

**글 본문은 평서체(`~다`).** 존댓말을 섞지 않는다.

```
O  그걸 안 해서 검수 사이클을 한 번 더 돌았다.
X  그걸 안 해서 검수 사이클을 한 번 더 돌았습니다.
```

**예외 — 직접 화법은 존댓말.** 독자에게 말을 거는 자리다. 글이 아니다.

- 히어로 인사 ("안녕하세요, 개발자 신성무입니다")
- CTA 버튼, UI 라벨, 폼 안내
- 블로그 목록 페이지의 리드 문구

이 둘을 헷갈리지 않는 기준: **화면을 설명하면 존댓말, 사건을 서술하면 평서체.**

## 2. 문단과 리듬

- **한 문단 = 한 생각.** 보통 2~4문장. 한 생각이 길면 문단이 길어도 된다.
- **짧게-길게 섞는다.** 짧은 문장만 이어붙이면 숨이 가쁘고, 긴 문장만 이으면 눈이 미끄러진다.
- **한 줄짜리 문단은 아껴 쓴다.** 글 하나에 한두 번, 진짜 전환점에서만.
  남발하면 리듬이 아니라 틱처럼 읽힌다.
- 긴 문단이 세 개 연속되면 사이에 코드·표를 끼운다.

```
O   녹음, 채점, 피드, 공유까지 다 붙이고 테스트도 돌린 뒤였다.
    사유를 열 때만 해도 어느 기능이 걸렸나 싶었는데, 코드 얘기는
    한 줄도 없었다. 이름이 틀렸다고 했다.

X   사유를 열었다.
                          ← 끊는 게 능사가 아니다. 세 문장이
    코드 얘기는 없었다.       한 호흡이면 한 문단으로 둔다.

    이름이 틀렸다고 했다.

X   사유를 열어보니 코드에 대한 지적은 전혀 없었고 대신 앱 이름이
    콘솔 등록값과 일치하지 않는다는 내용이었는데, 확인해 보니 실제로
    displayName이 달랐고 아이콘도 비어 있었다.
                          ← 반대로 너무 길다. 한 문장에 사건이 셋.
```

## 3. 구조 — 답을 먼저 말하지 않는다

사건이 있는 글은 **문제 → 삽질 → 진짜 원인 → 교훈** 순서로 간다.
결론을 서두에 박으면 읽을 이유가 사라진다.

단, 순수 참조성 글(설정값·명령어 모음)에는 이 구조를 억지로 씌우지 않는다.
이야기가 없는데 이야기인 척하면 오글거린다. 그럴 땐 그냥 표와 목록으로 간다.

**제목은 결론이 아니라 긴장을 담는다.**

```
O  Next.js를 Docker로 배포할 때 standalone을 안 써도 되는 경우
X  Next.js Docker 배포 가이드

O  앱인토스 검수에서 반려당한 이유가 코드가 아니었던 건
X  앱인토스 검수 반려 사유 정리
```

## 4. 구체적으로 쓴다

숫자가 있으면 숫자를 쓴다. 없으면 그 자리에 형용사를 채우지 말고 문장을 지운다.

```
O  배포 시간이 15~20분에서 4분대가 됐다.
X  배포 시간이 대폭 단축됐다.

O  87개 URL, 34개 JSP, 80여 개 SQL을 옮겼다.
X  대규모 마이그레이션을 수행했다.
```

**감정을 직접 말하지 않는다. 상황으로 보여준다.**

```
O  로그 한 번 보려면 부산까지 가야 하는 구조였다.
X  정말 답답한 환경이었다.
```

---

## 5. 실수를 숨기지 않는다

이 사이트 글의 흡입력은 절반이 여기서 나온다. 잘 된 것만 적으면 홍보물이 되고,
홍보물은 아무도 안 읽는다.

- 처음에 뭘 잘못 짚었는지 쓴다
- 사용자/리뷰어에게 지적당한 것을 쓴다
- 아직 못 고친 것도 쓴다 ("남은 것도 정직하게" 섹션)

단, 자학은 하지 않는다. 사실만 적고 넘어간다.

## 6. 코드

- 코드 블록 **앞에 왜 이걸 보는지 한 줄**을 둔다. 코드가 설명을 대신하지 못한다.
- 코드 안 주석은 "무엇"이 아니라 **"왜"**를 적는다.
- 실제로 돌아간 코드를 쓴다. 지어낸 예제는 티가 난다.
- 언어를 명시한다(` ```java `). 하이라이팅이 붙는다.

```
O  // 검색을 빠르게 두 번 누르면 먼저 보낸 요청이 나중에 도착해 화면을 덮는다
X  // 요청 ID를 증가시킨다
```

---

## 7. 쓰지 않는 표현

| 금지 | 대신 |
|---|---|
| `~할 수 있습니다` (기능 나열) | 실제로 그걸로 뭘 했는지 |
| 정말, 매우, 굉장히, 아주 | 삭제하거나 숫자로 |
| 혁신적인, 강력한, 최적의 | 삭제 |
| 이모지 (본문) | 사용 안 함 |
| `!` 남발 | 문장당 0개 |
| 영어 직역투 (`~에 대해서`, `~를 통해서`) | 우리말 어순으로 |

## 8. 체크리스트 (발행 전)

- [ ] 어미가 평서체로 통일됐나 (직접 화법 제외)
- [ ] 세 문장 넘는 문단이 있나 → 자를 곳 찾기
- [ ] 형용사로 때운 자리가 있나 → 숫자 또는 삭제
- [ ] 결론을 서두에 흘리지 않았나
- [ ] 실수·미완이 한 군데는 적혔나
- [ ] 코드 블록마다 앞에 한 줄 설명이 있나
- [ ] `summary`가 목록·검색결과·RSS에서 그대로 읽히나
